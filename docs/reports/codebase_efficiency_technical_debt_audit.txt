OPTIMIZE
======================================================================

O1. Discord RPC SET_ACTIVITY sent once per second while playing

What: NowPlayingManager.userContentController (:422) calls
DiscordRPCManager.shared.updatePresence(state:) on every message; the
observer JS guarantees a post every ~1s while playing (1000ms
setInterval + video events).

Why: Each call -> queue.async -> rebuild JSON -> sendFrame (socket
write) -> drainSocket, even though presence would persist on the RPC
connection.

Evidence: Observer JS :351-356; updatePresenceInternal :213-292 always
sends when _isConnected.

Additional waste: When Discord is not running, every update runs
findDiscordIPCSocket() (30 fileExists(atPath:) stat calls across /tmp,
TMPDIR, envTMP x 10 sockets) at ~1Hz during playback.

Impact: Continuous IPC writes + stat syscalls every second of playback;
needless battery/syscall churn. Presence only needs refreshing on
track/pause changes (Discord’s local RPC keeps the activity).

Fix: Throttle to track-change/pause transitions or a 15s cadence;
early-return when !isConnected instead of re-probing every second.

Confidence: high. Priority: P1.

O2. 1Hz full-state heartbeat even when nothing changed

updateNowPlaying(false) posts while playing even if title/artist/time
barely changed; Swift-side builds a fresh PlaybackState, overwrites
currentState, fires notifyObservers (2 live observers) on the main
thread, and re-renders play-icon + waveform every second.

OPTIMIZE: Gate the heartbeat to skip when currentTime/isPlaying delta is
negligible (like the existing paused-guard). Massive, loud, but works;
the extrapolation already makes sub-second accuracy meaningless. P2.

O3. Centered-lyrics 10Hz timer (displayTimer at 0.1s)

CenteredMenuBarLyricsWindowController.updateLyricsFrame (:143) runs
every 100ms while lyrics are enabled and playing. Each tick calls
state.getAccurateTime() + a linear scan SyncedLyricsParser.
activeLineAndWord, and when unchanged does almost nothing, but when it
changes it also recomputes font width + repositions the window.

Since only line-level text is shown (no word-level highlight), 10Hz is
far more than needed; a 1Hz tick aligned to state updates is sufficient
and removes a perpetual 10Hz main-thread timer. OPTIMIZE. P2.

O4. URLCache.shared capped at 0.5MB memory / 2MB disk
(YTMWebView.swift:21-22)

What: Tiny cache + DynamicIslandPlayerView.loadArtwork does a manual
URLCache check then Data(contentsOf:) (which does not reliably consult
the process URLCache) and re-fetches artwork on every panel re-show if
evicted.

Why: 0.5MB stores only a couple of full-size artwork JPEGs -> repeated
network re-downloads of the same album art; the per-URL NSCache only
holds 44px thumbnails.

Evidence: DynamicIslandPlayerView.loadArtwork :943-980; URLCache.shared
mutation in YTMWebViewContainer.init.

Impact: Redundant network/CDN hits + latency on re-open.

Fix: Raise memory capacity (e.g. 16-32MB) or use URLSession on a
dedicated cache configured for artwork (LRU). P3.

O5. Notification artwork: full temp-dir scan on every track change

TrackNotificationManager.downloadImage (:69-73) calls
contentsOfDirectory on the whole temp dir and deletes all ytm_art_*
files on every track change, before downloading fresh art that the
player already downloaded.

O(n) scan + duplicate image download per track; only ever needs the
latest file overwritten (single temp file). OPTIMIZE. P3.

O6. EdgeVolumeEngine auto-reconnect Timer runs forever

autoReconnectTimer (10s, :271-279) is scheduled in
setupLockWakeObservers() regardless of isEnabled and never invalidated
on disable -> a repeating main-thread timer alive for the whole app
lifetime even for users who never enable gestures (the default-off
case).

OPTIMIZE: Gate with isEnabled or start lazily in start(). P3.

RISK
======================================================================

K1. Linear time extrapolation can drift / run backward

PlaybackState.getAccurateTime() (:36-40) extrapolates currentTime +
(now - hostTimestamp) * playbackRate using the anchor from the last 1s
message.

During buffering/network stalls the anchor keeps advancing while
video.currentTime stalls -> the extrapolation runs ahead; on the next
message it snaps back.

Used by: progress bar, seek labels, Discord timestamps, lyrics
highlight.

Correctness is approximate by design and usually <=1s, but a dropped/
queued message can produce a visible backward jump in the lyrics
highlight and progress thumb.

Acceptable trade-off; worth a monotonic clamp per active track. P2.

K2. System idle-sleep assertion held unconditionally for the whole
session

BackgroundMediaController.startPreventingSleep()
(kIOPMAssertionTypePreventUserIdleSystemSleep +
.idleSystemSleepDisabledProcessActivity) is released only at
termination.

Combined with AppDelegate calling it again after init() already did
(no-op due to assertionID guard), this means the Mac will not idle-sleep
even when music is paused/stopped — a real battery/user-experience
concern.

Consider scoping the assertion to “isPlaying” only. Authorization
kIOPMAssertionTypePreventUserIdleSystemSleep is the app-name-honest
choice already. P2 — note, not necessarily change.

K3. Hard-coded dev-machine path in
NativeGestureTutorialWindowController.loadHtml (:67)

Falls back to: /Users/harshshirke/local/projects/mp3kal/trackpad.html

when the bundled resource is missing.

This is a personal absolute path baked into production code; on any
other machine it either silently loads a stale/nonexistent file or opens
a visible broken window.

RISK. Should only use Bundle.main (the build script does copy
trackpad.html). P2.

K4. NowPlayingManager.setupInWebView re-adds the observer user script on
every call

handleWebContentTermination calls setupInWebView again (:94-96);
WKUserContentController.addUserScript appends without removing the old
script, so the userContentController can end up with two copies of the
~250-line script (runtime-guarded by window.ytmObserverInjected, so
functionally harmless, but duplicated injection per page load forever).

RISK/minor. Track the injected script and removeUserScript before add.
P3.

K5. Window/clamp logic duplication risk between panel paths

StatusItemManager.positionCustomWindow (:316) and panelDidMove (:254)
each independently recompute targetX/targetY + clampFrameToVisibleBounds
with slightly different clamp paths (margin 8 vs 12 vs 0).

On non-primary screens / freshly reconnected displays these two can
disagree, producing a mid-animation jump on drag — hard to test but the
same math exists in two shapes.

REFACTOR into one frame(for screen:, width:, height:) helper. P3.

KEEP (justified complexity — do not touch)
======================================================================

-   Observer-JS bridge in NowPlayingManager — the entire heartbeat/
    control/JQ-scrape approach is inherent to driving YouTube Music with
    no public API; the multi-priority fallbacks (DOM > Polymer data
    model > player API) are what make it resilient. Keep, even though it
    is ~1,000 lines of embedded JS.

-   Web-content crash recovery machinery (YTMWebView termination ->
    snapshot -> restore -> watchdog) — genuinely valuable and carefully
    done.

-   EdgeVolumeEngine private MultiTouch framework usage +
    ActiveEngineBox relay — inherently unsafe-looking C interop but
    necessary for the headline gesture feature; the relay box correctly
    avoids the retain cycle the callbacks otherwise create.

-   FreshViewRouter… DisplayManager — small, used, single-purpose.

-   DiscordRPCManager socket/opcode layer — correct and isolated; only
    the update throttle is wrong, not the design.

-   native -> adaptive legacy mapping in PlayerDesign.current —
    intentional migration; leave the enum case as legacy-read-only.

-   Position persistence + display-change clamping in StatusItemManager
    — a feature (user’s floating placement survives display changes);
    keep.

6.  Overall technical-debt assessment

Moderate-to-heavy, concentrated and very cleanable.

The debt is not distributed subtly — it is the volume of unused/
duplicated code plus one systemic performance smell (the per-second RPC
push).

Core live paths (the panel player, StatusItemManager, YTMWebView,
NowPlayingManager bridge, gesture engine) are carefully engineered and
internally consistent.

A focused cleanup pass — delete dead code (R1-R9), dedupe shared helpers
(S1-S7), and throttle Discord/lyrics timers (O1/O3) — would remove
~1,600 lines and a 1Hz socket+stat loop with low regression risk,
because the removal targets are provably unreferenced and the perf
changes preserve behavior.

The highest-risk refactors are S3/S4 (shared JS) and K5 (unifying clamp
paths), which should be done carefully with manual playback testing.
